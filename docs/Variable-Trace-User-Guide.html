Variable-Trace 上手指南

版本 1.1.0 · 基于 MCUViewer 1.1.0 的开源分支

这是什么

一个跑在 PC 上的单片机实时调试工具。它通过调试探针（J-Link 或 ST-Link）的 SWD 接口直接读写目标芯片的 RAM，把变量画成实时波形；也能接住芯片通过 SWO 送出的跟踪数据。

它解决的核心问题：调试嵌入式程序时，往往想看着某个变量随时间怎么变，而不是在某一个断点上停下来看它的瞬时值。

使用门槛很低——程序里不需要加任何打印语句，只要变量还在，就能看。代价是这东西只能看全局变量或静态变量，因为它们的地址在程序整个生命周期里固定不变。

需要什么

项目要求
调试探针J-Link 或 ST-Link，一根即可
接线变量视图与记录器只需 SWDIO / SWCLK / GND；跟踪视图另加 SWO
固件以 debug 模式编译，保留符号表
符号文件*.elf 或 *.axf（两者是同一种容器）
变量要求定义在文件作用域、带 volatile 修饰

五分钟跑通

以下是变量视图最短的启动路径。

  1. 打开采集设置
    顶部菜单 Options → Acquisition settings...。这个窗口的内容跟着当前页签走，变量视图和跟踪视图各有各的一份。
  2. 选择符号文件
    选中你编译产物里的 *.elf 或 *.axf。变量地址就是从这里读出来的。
  3. 导入变量
    点 Import variables from *.elf，勾选需要的变量后确认。
    如果某个变量没被认出来，用 Add variable 手动填名字也可以，之后再点 Update variable addresses 补上地址。
  4. 选探针并填参数
    探针类型选 J-Link 或 ST-Link。
    J-Link 用户注意「Target name」必须手填，而且要用器件的基础名，不要带封装或温度后缀——例如 STM32F103C8。名字为空、末尾有空格、或者带了后缀，J-Link 都会拒绝连接。
  5. 解析地址
    点 Update variable addresses。变量列表里的类型和地址应当从 NOT FOUND! 变成有效值。这一列还有 NOT FOUND! 就说明符号文件不对，或者这个变量被编译器优化掉了。
  6. 把变量拖进绘图区
    从左侧列表拖到右边的绘图区。一个绘图区可以叠多条曲线；需要 X-Y 图就在新建绘图区时把类型选成 XY，再指定横轴变量。
  7. 开始采集
    确认探针接好、目标已供电，点那个写着 STOPPED 的按钮。它会变成 RUNNING，曲线开始动。
    右上角会显示探针名称、连接状态和一串 sampling: X Hz——那才是实际达到的采样率。
J-Link 首次连接较慢 从点击开始到第一条曲线出现可能要几十秒，这属于正常现象。如果一直没动静，先看日志窗口里的错误信息。

三条数据通路

理解这个软件的关键，是分清数据从哪儿来。三条通路的原理不同，适用场景也不同。

通路数据怎么来实测速率特点适合看什么
变量视图 主机逐个变量向探针索取 约 4.2 kHz（单变量） 实时；每加一个变量，所有变量一起变慢 普通控制逻辑、状态机、慢速物理量
跟踪视图 芯片通过 SWO 主动送出 由 SWO 带宽决定，可达 MHz 级 需要在代码里写 ITM 语句；对程序运行影响很小 函数耗时、中断频率、高频信号
记录器 目标的定时中断自己写进目标内存的环形缓冲 由目标侧时基决定（示例固件为 20 kHz） 录制期间不占用调试链路；支持触发与预触发；事后整块取回 比调试链路更快、且需要与事件对齐的信号

该用哪一条

  • 信号变化在几百赫兹以内，想边调边看 → 变量视图，最省事
  • 要看某段代码执行了多久、中断是不是按预期频率进 → 跟踪视图
  • 信号快到变量视图抓不住，或者想在某个条件出现时抓一段 → 记录器
变量视图的速率是怎么被限制的 软件会把普通 RAM 中重叠或严格相邻的变量合并成连续块读取，所以一段连续地址通常每个样本只需要一次探针往返。稀疏地址、外设寄存器和不支持块读取的通路会保守地退回精确读取。实际速率仍取决于探针延迟、地址布局、绘图和 CSV；同一个变量被多张图引用不会重复采集。

组与绘图区

组是最高一层容器，分两种类型：

  • Sampling group（采样组）——变量视图使用，由探针读取
  • Recorder group（记录器组）——记录器使用，由目标自己采样

只有活动组里的变量会被采集。切换活动组就等于切换看哪一批数据。

别把记录器组设为活动组 当前实现里，把记录器组切换成活动组会让采集循环去读它的变量，出现意料之外的行为。

性能诊断与 CSV 状态

采集稳定至少 1 秒且完成 100 个样本后，右上角会在确有压力时显示诊断。悬停指示器可查看请求/实际采样率、期限丢失、探针耗时、绘图缓冲等待和 CSV 队列占比。

提示含义与处理
Probe latency探针读内存占主要时间；检查连接、SWD 速度和探针型号
Address fragmentation变量地址过于分散，无法合并成少量块读取；优先把需要同时观察的数据放在连续 RAM 区域
Render contention绘图帧或缓冲复制影响采集；缩短可见时间窗、减少可见曲线或降低 GUI 负载
CSV backlog写盘跟不上或文件写入失败；检查日志目录、磁盘空间和介质速度
Deadline limited请求频率超过当前组合能稳定达到的频率，但没有单一消费者占主导；降低目标频率
CSV 过载不会停止变量采集 队列满、文件打不开或写入失败时，本轮 CSV 会停止并排空已经接受的样本，变量采集继续。右上角出现 CSV stopped，采集设置页会显示原因、时间、文件路径和样本计数。不会静默覆盖旧行，也不会自动降低采样率。

任务视图

变量视图回答"这个变量现在是多少"。任务视图回答另一类问题：谁在跑、谁在等、在等什么、等了多久。 它不读固件里的任何统计，全部从 FreeRTOS 的内核结构里读出来，所以不需要改编译选项，也不需要固件配合。

在全局设置里打开任务视图（配置文件 global.json 的 rtos.enabled）， 然后切到 Task 页签。它和变量视图共用同一次采集：探针连着、采着，任务视图才有数据。

它读的是内核自己的工作数据 就绪、延时、挂起、终止四张表，每个任务的等待对象，同步对象的持有者与等待人数， 以及运行时间统计。这些是内核自己为调度而维护的，软件只是把它们读出来并做算术。

录制与回放：把一段现场带回去看

面板最上面一行是数据来源：眼下这张表是探针刚读回来的，还是几天前录下来的文件。 两种情况只会有一种成立，这一行也只会说一件事。

这一行显示意思
record · open a recording正在看实时目标。按 record 选一个文件（默认名字带开始时刻，后缀 .vtrec），按 open a recording 打开以前录的
recording 文件名 · 1204 轮 · 602.1 秒 · 2.1 MB正在录。旁边的 stop recording 结束并关文件
playing back 文件名 · 1204 轮 · 602.1 秒 · 第 401 轮，共 1204 轮正在看文件。旁边是 back to live 与 open a recording

录的是界面看到的每一轮：表里的每个字段、发现区的每条判断、泳道的每个采样， 回放时都一模一样。任务视图的轮次约两秒一轮，所以一段十分钟的记录只有几百轮、几兆字节。

切换记录也写进文件：目标报的每段"谁从什么时候跑到什么时候"跟着它所在的那一轮 一起写。打开记录之后，泳道是区间画法、事件列表有行可点，都和接探针时一样。 更早录的文件没有这一段：它们照样能打开，只是事件列表会说明"这份记录写在开始保留切换记录之前"—— "没记"和"没切"是两件事，不该让一个空框去猜。

回放时时间线就是进度条：在色带上点一下（钉住一个时刻），表格、发现、选中详情 就都换成那一刻的样子；说明行里的"第几轮，共几轮"跟着走。不钉的时候停在最后一轮。 拖动窗口、缩放窗口都只改看哪一段，不改看哪一轮。

录制与回放不会同时成立 回放时开始采集会把文件关掉（新的采集是新的时间轴）；录制的过程中开始采集也会先把文件收尾—— 一轮记录只属于一次采集，跨两次采集会在同一根时间轴上画两段互不相干的运行。 回放时采集可以继续跑：变量视图照常更新，任务视图只显示文件。

导出成 CSV

.vtrec 只有这个程序能读。想算点别的——这一小时的栈占用有没有往上爬、哪个任务 吃掉了多少时间、那个阻塞到底多久来一次——用表格软件算比在界面上看快。所以回放时这一行下面 有一个 export CSV：每个任务每轮一行，列和界面上的表一样。

列内容
round / at_s第几轮，以及那一刻在时间轴上的秒数。每行都带，方便筛选和分组
task / address名字与控制块地址。这两个是身份，不是读数，所以任务这一轮没读到也会写
state / found_on状态，以及这条状态是从内核哪张表上读到的（suspended 表上、事件项为空，就是"无超时等待"）
priority / base_priority当前优先级与创建时的优先级。两者不同就是被继承了
stack_used_bytes / stack_size_bytes / stack_free_percent水位、声明大小、剩余百分比
cpu_share_percent它在这段窗口里占任务时间的百分比
waiting_on在等的对象名，没有就是空

这一轮没测到的格子是空的，不是 0。空表示"没读数"，0 表示"读到了，值是零"—— 这两件事在表上是一个破折号与一个数字的区别，在 CSV 里就是一个空字段与一个 0。把它们混起来， 后面算平均值就会把没测到的轮次当成零拖低。

文件默认叫记录文件的名字、后缀换成 .csv，写在记录旁边。导出的是整份记录， 不受表格当前筛选和排序的限制——筛掉几行再导出，那份文件就跟记录对不上了。

导出只有回放时才有 实时采集时程序只保留当前这一轮，没有"整份"可导。想把一段正在跑的东西留下来， 先按 record 录下来，再打开它导出。

任务表

列含义
Task任务名
Priority当前优先级。显示成 3 (1) 表示当前 3、创建时 1——这叫优先级继承：它持着一把别人想要的锁，内核临时把优先级借给它。这一列着色时也是这个意思
StateRunning / Ready / Blocked / Suspended / Terminated

Waiting on阻塞时等的对象名；读的是内核的对象等待表，不是任务表

表里一行都读不到数据时显示 -，那是"没有读数"，不是"零"。 栈水位靠宿主扫栈里的 0xa5 填充，一轮扫不完所有任务，所以每行的读数各带年龄——这一点在下面的"选中任务详情"里能看到具体秒数。

行数是固定的，不会随某一轮读到几个任务而增减。内核在采集一轮的几毫秒里仍在改自己的链表， 所以一轮读到十四个任务、下一轮读到十一个，是正常的读数，不是任务消失。表格的行来自这次会话见过的 全部任务：某一轮没读到的那个，行还在，名称和地址照旧，其余每一列都是 斜杠 /，整行压暗，鼠标停上去会说上一次读到它是在几秒前。

标记意思
-这一轮读到了这个任务，但这个字段没有读数（例如栈还没轮到扫）
/这一轮根本没读到这个任务，整行没有任何读数。行留着，因为它还在这张任务表里

没读到的行在任何"收窄"的问题下都不出现（只看阻塞、只看异常、只看高占用、状态、优先级下限）， 因为那些问题问的是这一轮；只有"全部任务"里它占一个位置，按问题排序时排在最后。 它的泳道也还在，画成"没有读数"而不是"没在跑"。

默认按任务名排（A→Z，表头的 Name 上有个箭头），行因此钉在固定位置：任务名不变， 位置就不变。表下面那一行写着现在用的是哪种顺序，点任一列头改成按那一列排。

还有一种是问题排序——栈告警、阻塞且有等待对象、优先级被继承，然后按基础优先级 （创建时的那个）从高到低、再按名字。它回答"我现在该看哪个"，代价是行会动：某个任务 一被阻塞就跳到上面去。所以它不再默认开启，旁边那个 back to problem order 随时切过去， 切回来点一下 Name 列头。选的是哪种会记住。

要看"谁最忙"，点一次 Task share 列头——那才是在问这个问题。

点任意一行都会选中那个任务：时间线里对应的泳道高亮，对象表指向它在等的对象， 右栏的详情跟着换。列可以拖动改宽，也可以在表头上右键显示/隐藏。

空格 是同一个开关。它在文本框里有焦点时不管用——那时空格是文字。

摘要与筛选

状态条下面一行是摘要：任务总数，接着四个带色点的计数（运行 / 就绪 / 阻塞 / 挂起）， 后面可能有"栈告警"与"优先级被继承"两个计数。色点的颜色与时间线图例是同一套。

点一个计数，表格就只留下那一类任务；再点一次放开。选中的计数会有一层淡色 填充和一圈边框，没选中的只有色点和数字——所以"这是状态的颜色"和"这个筛选生效了"是两件事。

计数下面那一排是四个问题，一次只问一个。它决定"看哪些任务"，下面的 筛选条件在这个范围里再收窄。

问题留下什么
all tasks这一轮读到的每个任务
problems only栈剩余到或低于告警阈值的、优先级被继承抬高的，以及"发现"里点到名的任务（疑似死锁环上的人、无超时等待者、就绪却一直没被切入的）
blocked only在等某个东西的任务，不管这段等待有没有超时
high share only任务时间占比到或高于下限的任务。选中之后旁边出现 task share >= [10] %，可以当场改

problems only 故意不包含"每个阻塞在对象上的任务"：内核健康的时候那是大多数任务， 一个回答"全都有问题"的筛选没人会用第二次。鼠标停在按钮上有这一段的原话。

同一次只能问一个问题，所以按钮是互斥的。blocked only 与摘要里那个"阻塞"计数 说的是同一件事，点其中一个，另一个跟着对。选一个状态计数或状态多选会退出 blocked only， 避免两个控件各说一半、表格空掉却看不出原因。

控件作用
search by name按任务名筛
states多选状态，四类各带自己的色点；上面那排计数是它的快捷方式，两边改的是同一个条件
stack alerts only只留下栈剩余低于阈值的任务
clear filters一次清掉全部条件，包括上面那个问题。没有条件时它是平面的，看起来就是"没得清"
stack free <= 20 %栈告警的阈值，0 关闭告警
priority >=只有不低于这个优先级的任务留下

这一行右端写着"14 个里显示 14 个"，也就是当前筛选之下还剩多少行。筛完一行不剩时， 那一行改成说原因——空表格没有一句话，看起来像界面坏了。

发现（Findings）

诊断结果写在单独的一段里，标题带数量（Findings 2）。这一段一直在， 高度固定两行：有问题时是那两条最严重的，没问题时第二行写"这一轮没有发现"。 它曾经在没有问题时整段消失，结果条数一变，下面的筛选和表格就上下挪一次。

每条前面有一个字符表示严重程度，颜色只是重复它：

标记意思哪几条
! 红会卡住：这条不解决，任务就不往前走疑似死锁、无超时等待
! 橙警告：调度器在做不该做的事就绪但从未被切入
i 蓝灰提示：内核在做它该做的事，只是值得知道优先级继承

每条都带一小段链子，读作等待者 → 对象 → 持有者。整行都可以点： 点它会选中链子上的第一个任务、它等的对象，表格、泳道、对象表同时定位过去。 点的时候会先清掉筛选——目标被筛掉时"定位"落在空处，看起来像点了没反应。

右键一条发现可以复制整条链（inv_high -> mtx_inv -> inv_low）， 贴进报告比"优先级继承"四个字说明得多。时长在每行右端，列对齐，便于比较。

诊断它说明什么什么情况下不报
优先级继承 某个持锁任务的优先级被抬高了——内核只在有更高优先级的任务等这把锁时这样做。链子读作：等待者 → 锁 → 持有者 ——
疑似死锁 两个或更多任务各自等着下一个任务手里的锁，绕成一个环 环在两轮之间自行解开时看不见——一轮只是一个采样，所以说"疑似"
就绪但从未被切入 一个任务比实际在跑的那个优先级更高，且最近两秒每一轮都是 Ready。抢占式调度器不该这样 有同级或更高优先级的任务也 Ready（调度器跑的是对的）；在跑的任务正处优先级继承中（它持着别人要的锁）；只持续了一两轮（可能是切换在途）
无超时等待 任务阻塞、但等待没有超时——它只有在那个对象被给出时才会再跑。会附带"已经等了多久" 故意挂起（Suspended）的任务；有超时的阻塞（内核知道何时唤醒它）
"不报"和"报了"一样重要 这些判据的价值首先在于不乱报。比如"Ready 却没在跑"本身是正常调度——低优先级任务本来就在等， 所以只有当一个任务的优先级高于实际在跑的那个时才算异常。判断时用的是它创建时的优先级， 因为被继承的那个号码是等待者的，不是它自己的。

同步对象与时间线

同步对象表列出内核里注册过的队列、信号量、互斥量：类型、容量、当前计数、各有几个任务在等、谁持着。 点了任务行，相关的对象会跟着高亮。

时间线把每个任务画成一条泳道，横轴与变量视图共用。跟随光标打开时，窗口跟着变量视图的光标走： 双光标是区间，单光标是居中。缺某一轮读数的任务画成"没有读数"，不画成"没在跑"——这两件事不一样。

每条泳道的高度是固定的（22 个单位，按界面缩放走），任务多一条少一条都不会让别的泳道变粗变细。 装不下时列表在框内滚动：把指针放在左边的任务名上滚轮，或者按住 Shift 在任意位置滚轮； 框右下角会显示"第几条到第几条 / 共几条"。指针放在绘图区（时间轴那半）滚轮仍然是缩放时间窗。

框的高度按这次会话见过的任务数算，不按当前筛出来的条数算——所以筛筛选选不会让下面的 同步对象、钉住时刻、选中任务跟着上下跳；只有真的有新任务出现时，框才会长高一条。

框下面两块（同步对象、钉住时刻）各有固定的高度，内容多了在框里滚动， 不往下面的块上压。钉住一个时刻、取消钉住、某一轮没读到运行中的任务——这些都会让块里的字变， 不会让块挪位。右栏剩下的高度归泳道：它只随窗口大小变，不随任务数变。钉住框恒为"标题 + 三行"（时间、运行、四类计数），没有值的那一行写一个短横， 不整行消失。工具条上的"取消钉住"一直在，没有钉住时是灰的——一个时有时无的按钮会把 旁边的开关挤到下一行，连带把下面所有东西推下一行。

四种状态的颜色是为红绿色弱者挑的：运行是浅绿、就绪是橙黄、阻塞是琥珀、挂起是中性灰， "没有读数"是一块深棕。前三个都落在红绿这条轴上，靠的不是色相，而是明度—— 近白的绿、亮的黄、深的琥珀，明度差在红绿色弱下是不会丢失的那一部分。按模拟量，四色之间最近的 一对仍有 CIELAB 二十九分的差距（原来那套绿/琥珀只有九分）。图例里的方块还各带形状 （实心／斜线／点线／空心），颜色不是唯一的通道。

这块矩形有两层意思，用位置分开，不需要记修饰键：

点在哪里做什么
泳道名字那一列选中这个任务，和点表格里那一行同义；它在等的对象也一起选上
绘图区（右边的彩色带）钉住这个时刻，右栏出现"Pinned moment"，说那一刻在跑谁、四类各几个

泳道的顺序默认按基础优先级（创建时的那个），这样一条泳道在轮次之间不会移动—— 按当前优先级排的话，一有继承整张图就翻一遍。头部有跟随表格顺序开关， 打开后泳道按表格当前的排序走；说明行会写明现在是哪一种。

筛选也管泳道：表格只剩三行，图上就只剩三条泳道——"哪几个任务值得看"是一个问题， 泳道就是看的地方。说明行会写"13 个任务里有 4 个有泳道"，因为少掉的泳道很容易被读成"这些任务没在跑"。 筛到一个不剩时它说的是"筛选之后没有任务可画"，而不是"这一轮没有任务"——那是关于目标的另一句话。

选中任务详情

它在任务表下面，不在右栏：它是"现在这一个任务"的细节，和表格问的是同一件事， 点一行，视线往下就看得见。表格本身按行数定高，最后一行下面就是这一块，不在窗口半腰里留一大片空表。

这块地方有四个页签共用：Selected task、Waiting chain、 Events、Tracks，点哪个就把这块高度给哪个。四件事都是"一个时间读一件"， 并排放只会让每件都矮一截。切页签不会让表格换高度——这一块的高度是固定的。

表格是横向比较的形状，读单个任务要看的是句子：

行为什么单列一行
Address控制块的地址，贴进报告或脚本里用
Found on这条状态是从内核哪张表上读到的。它和 State 不是一回事：挂在 suspended 表上、事件项却是空的，那就是"无超时等待"
Priority被继承时写成 3 (was 1) - inherited while a lock is held
Stack用量、剩余百分比，以及这个读数是几秒前扫的。扫描一轮只扫几个任务，所以每行的年龄不同
Task share占比，以及分母是什么：任务用掉的时间里它占多少，统计窗口多长
Problems这个任务被哪几条发现抓到（waiting with no timeout 333.1 s），没有写 -。表格里看不出原因的两种——死锁环上的人、就绪却被一直跳过的任务——在这里说明

标题右边的 copy 把同样的信息压成一行放进剪贴板，例如 stuck 0x20001B60 blocked priority 1 stack 136/504 (26% used) share 0.0% waiting sem_stuck。 鼠标停在按钮上能先看到这一行。

切换记录：时间线是怎么来的

时间线有两种画法，取决于数据来源：

来源时间线画成代价
目标的内存环形缓冲（默认） 一条条运行区间：某个任务从被切入到被切出跑了多久 两轮之间被覆盖的记录会丢，丢了多少如实显示（lost）。条带的疏密就是这个数在说话
每轮一次的采样（没有环形缓冲时） 一个个点：那一刻谁在跑 看不到区间之间的形状

目标侧要提供切换记录，需要一处固件改动（一个 trace 宏）。参考实现与说明在 example/rtos_trace_port/event_ring/，编译开关是 make EVENTS_ON=1—— 默认不进固件，符合"不给固件加约束"这条原则。

除了内存环形缓冲，还可以走 ITM/SWO 与 RTT 两条通路 （global.json 的 rtos.eventsTransport）。它们的现状见"限制与已知问题"。

等待链：谁在挡着这个任务

选中一个任务之后，表下面的 Waiting chain 页签把它卡在哪儿画出来：一个方框是一个任务， 一个方框是一个同步对象，箭头只有两种，waits for（它在等这个对象）和 held by （这个对象在谁手上）。链会一直走下去，直到没人再等，或者绕回已经画过的那一个。

┌───────────────────────────────┐
│ inv_high        blocked, 优先级 3 │
└───────────────┬───────────────┘
                │ waits for
┌───────────────▼───────────────┐
│ mtx_busy        mutex 0/1, 1 个在等 │
└───────────────┬───────────────┘
                │ held by
┌───────────────▼───────────────┐
│ led              running, 优先级 2 │
└───────────────────────────────┘

方框左边那条竖线的颜色就是这个任务的状态色，和泳道上是同一套；点方框等于在表格里点它那一行。 对象框里写着它被拿走几个、有几个在等——链只跟其中一个（持有者），其余的靠这个数字不丢。

绕回第一个方框就是死锁：最后一条箭头画成橙色、写"回到某个任务"，而不是再画一个方框。 重复的方框会让人以为链更长，而这几步绕回来的形状才是要看的东西。发现区里的"疑似死锁"说的也是这件事， 一处用文字说链条，一处用图说形状。

这张图是定格的，不是每秒重画。一轮大约两秒一次，而"谁在等谁"正是两轮之间最容易 变的东西：锁换了手、持有者变成就绪、等待变成了运行。跟着轮次重画的话，五个方框每秒重排两次， 眼睛还没找到位置图就换了——这跟"看不清"是一回事，跟"看得清但内容变了"不是一回事。

表头那行意思
定格于 12.4 秒前画的是选中那一刻的那一轮，之后没动过；这个数字每秒都在长
橙色 …，链已经变了现在这一轮的链和图上不一样了。图不动，只告诉你它过期了
橙色 …，这个任务这一轮不在表里它这一轮没被读到（或已经不在了）。图上还是它最后一次的形状
跟随最新一轮勾了 follow，每轮重画。想看它怎么变的时候用

refresh 抓当前这一轮重画一次；换选另一个任务会自动重抓——换任务是一个新问题， 接着上一个的图没有意义。

链会在两个地方停 一是没人在等（blocked 但等的是信号量、持有者是空）——那就只画一个方框； 二是它等的对象名不在内核的登记表里，这时页面上会直说"这个名字不在登记表里，链到这里断了"， 不画一个空的对象框。链最多六个方框，超过就截断——能截断是因为它不会再回到起点， 真绕回来的环一定在六步之内出现。

事件列表：把切换记录读成行

时间线画的是同一批记录，但宽度只能用眼睛量。"4.21 秒那一刻是谁"这种问题， 眼睛量不出来。事件列表就是这批记录的行式：时间、任务、跑了多久，从早到晚排。

它在左栏、任务表下面那块，从 Events 页签进——行该和行放一起， 右栏留给图形与时间。列表和它上面的表格用的是同一批任务名、同一套选中，点一行跳到那一刻之后， 右栏的泳道会同时亮出那一段。

做什么怎么做
停住列表勾 pause。停住的是列表不是目标，采集照跑；停住期间新到的条数写在旁边（19 new while paused）——一条悄悄停住的列表是会骗人的
跳到那一刻点任意一行。右栏的钉住时刻与时间线窗口、左栏的任务表都跟着换到那一刻
只看一个任务先在表格或泳道里选中一个任务，列表右上出现 only inv_mid，点它只剩这个任务的切换；它前面变成带叉的标签，点叉恢复全部
从这个任务看它的切换选中任务详情里的 Switches (5 s)：最近五秒被切入了几次，最多列三条，点一条同样跳到那一刻

反过来也成立：点列表里的某一行，那个任务就被选中——左栏详情块换成它， 它在列表里的其它行加一层底色。两边指的是同一个任务，不需要记住刚才在哪儿点的。

列表只留最近 600 段，表头写"600 of 48122"：滚过去比读得快，而整段时间线那边看得见。 计数永远报的是筛完之后的数，所以"只看 inv_mid"时会从四万多掉到一万三。

为什么没有"因果高亮" 切换记录里只有两样东西：哪个任务的控制块、目标自己计时器上的微秒数。它不记录为什么切换 （超时、被抢占、主动让出），也不记录那一刻在等哪个对象。要把"谁等谁"画到事件行上，得让固件在切换点 多写一个原因字节——那是给固件加约束，按项目原则不做。这一刻在等谁，读钉住时刻与 同步对象两块：它们说的是当前这一轮的快照，来源不同，不混在一起。

Tracks：另外四类事件

任务表说的是"每个任务怎么样"，Tracks 说的是"这台机器上还发生了哪些别的事"： 中断、故障、同步对象上的等待、堆的分配。每条轨道一条横带，横轴和泳道是同一条时间轴。

这一版你还是会看到一片空白，标题写着「没有接事件源」 界面的这一半已经在了，喂它数据的那一半还没接上——采集线程目前只把切换记录交给旧的 泳道，没有交给这条通路。等接上之后，这五条带子才会有东西。空白的带子和"没有发生" 是两件不同的事，所以这里宁可直说"没有接"，也不画一条空带子让人以为目标很安静。
轨道画什么
ISR每次中断的进出。嵌套的中断画成里外两层，不是两条并列的
Fault红点。点开能看寄存器（类别、CFSR、PC、LR）——哪一项没读到会明说
Sync等对象的那段时间，按"任务 + 对象"配对；超时结束的与等到的分开
Heap每次分配与释放，外加一条净变化曲线
Gap橙点。记录丢了的时候，这一列必须有东西——丢了是事实，不能画成安静

一条带子有多密，是按像素列算的：一列里有几条就画一次，浓淡三档。 一列塞了五十条的时候，逐条画出来和画一条是一模一样的。

Fault 与 Gap 不参与浓淡分级：它们用固定的红与橙，再挤也保持原色。 一个按"忙不忙"分级的聚合，会把最坏的那一瞬间和它的证据一起抹平。

右边那行数字里有一项容易看错：N 条无时间。这些事件确实发生了，但没带目标时间 （比如源没有时钟），所以放不到时间轴上——它们被计数，而不是被画在时间轴最左边冒充第 0 秒。

HTTP 接口（MCP）

  • 默认地址 http://127.0.0.1:7807/mcp，只监听本机

  • 提供 57 个工具，覆盖变量、绘图区、组、数据读取、采集、记录器、烧录、工程、任务视图与实例信息

  • 脚本调用时注意绕开系统代理，否则会拿到代理返回的错误

命令通道

  • 裸 TCP 行协议，默认端口 7808，默认关闭
  • 面向 PLC 与控制台脚本——那些不方便讲 HTTP 的环境
  • 每行发一次请求，每行回一次应答，格式是单行 JSON
  • 与 HTTP 接口共用同一批工具和同一套参数校验
多实例并存 同时开多个程序实例时，端口会自动向后寻找空闲值。

限制与已知问题

能力边界

限制说明
只支持 32 位变量uint64_t、double 暂不支持
变量必须是全局或静态地址要在程序运行期间固定不变
采样率有上限上限取决于探针、地址布局和消费者负载；连续 RAM 变量可合并读取，稀疏或外设地址仍可能随事务数明显下降
SWD 速度并非越快越好从 1 MHz 提到 4 MHz 提升明显，4 MHz 往上收益递减
记录器需要目标侧代码固件里必须集成配套的参考实现
个别探针会在读任务控制块时卡住表现是采集启动一两秒后自己停住，界面还在，数据不再更新。原因是探针的一次同步 USB 读等不到应答。到"采集设置"里取消 Task view: read control blocks（存进工程文件）——任务表会只剩状态和地址，但变量视图继续工作
任务视图只能看到被调度过的东西内核不维护"切换次数"，所以没有这一列；统计的是当前状态与最近的历史
SWO 与任务视图的读数不能共存（J-Link）一颗 J-Link 同时只服务一条连接。调试连接占着它时，SWO 那条连接连不上；跟踪视图能用 SWO，正是因为它独占连接。要改用 rtos.eventsTransport 时必须接受"任务视图读不到内核"
RTT 通路当前不可用目标侧已就绪，但 J-Link 的 DLL 能找到控制块、读不出数据。默认的数据通路是内存环形缓冲，不受影响

已知缺陷

现象规避方式
把记录器组设为活动组会导致采集异常不要这样操作
J-Link 的低端型号记录器带宽被限制在 1 kHz使用变量视图；或换用支持高速采样的型号
写值计划器只能编辑，不能执行用表格图的写值列，或走 API
采集刚启动的极短时间里，记录器触发可能不响应等采集稳定后再触发

常见问题

变量地址一直是 NOT FOUND!

  • 符号文件是不是当前编译产物？拷错或者版本旧了都读不到新变量
  • 固件是不是以 debug 模式编译的？优化器可能把变量整个消掉
  • 变量有没有加 volatile？没有修饰的变量可能被优化进寄存器，内存里根本没有它的位置
  • 变量是不是定义在文件作用域？局部变量不在符号表里

J-Link 连不上

  • Target name 是否填的是器件基础名，例如 STM32F103C8；带后缀或末尾有空格都会失败
  • 目标板是否已供电
  • 上一次调试遗留的坏会话可能还占着探针。用 J-Link 自带的命令行工具执行一次连接再断开，通常能清掉

采样率比设定的低很多

界面右上角显示的是实测值，不是设定值。先悬停右上角指示器查看自动诊断：探针延迟时检查连接和 SWD 速度；地址碎片时减少稀疏地址；绘图争用时减少可见数据；CSV 积压时检查磁盘；期限受限时降低目标频率。连续 RAM 变量通常可合并读取，因此变量数不再必然造成线性下降。

跟踪视图没有数据

  • System Core Clock 有没有填对
  • 预分频是否降到了探针支持的范围以内
  • 目标固件里有没有发送 ITM 数据
  • SWO 引脚有没有接上（变量调试用的三根线不够）

记录器读回来的值不对

  • 先确认 Detect 报出的时基与固件里配的一致
  • 采样期间改过组里的变量，会导致目标侧的打包方式与主机预期不符。重新开始一次录制
  • 出现 Overrun 提示说明缓冲被覆盖过，减小变量数或者缩短录制时间

关闭时提示保存工程，程序卡住不动

有未保存的改动时会弹出确认框。用脚本自动化时要注意这一点，无人应答会一直等下去。

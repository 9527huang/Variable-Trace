Variable-Trace 上手指南

版本 1.1.0 · 基于 MCUViewer 1.1.0 的开源分支

这是什么

一个跑在 PC 上的单片机实时调试工具。它通过调试探针（J-Link 或 ST-Link）的 SWD 接口直接读写目标芯片的 RAM，把变量画成实时波形；也能接住芯片通过 SWO 送出的跟踪数据。

它解决的核心问题：调试嵌入式程序时，往往想看着某个变量随时间怎么变，而不是在某一个断点上停下来看它的瞬时值。

使用门槛很低——程序里不需要加任何打印语句，只要变量还在，就能看。代价是这东西只能看全局变量或静态变量，因为它们的地址在程序整个生命周期里固定不变。

需要什么

项目要求
调试探针J-Link 或 ST-Link，一根即可
接线变量视图与记录器只需 SWDIO / SWCLK / GND；跟踪视图另加 SWO
固件以 debug 模式编译，保留符号表
符号文件*.elf 或 *.axf（两者是同一种容器）
变量要求定义在文件作用域、带 volatile 修饰

五分钟跑通

以下是变量视图最短的启动路径。

  1. 打开采集设置
    顶部菜单 Options → Acquisition settings...。这个窗口的内容跟着当前页签走，变量视图和跟踪视图各有各的一份。
  2. 选择符号文件
    选中你编译产物里的 *.elf 或 *.axf。变量地址就是从这里读出来的。
  3. 导入变量
    点 Import variables from *.elf，勾选需要的变量后确认。
    如果某个变量没被认出来，用 Add variable 手动填名字也可以，之后再点 Update variable addresses 补上地址。
  4. 选探针并填参数
    探针类型选 J-Link 或 ST-Link。
    J-Link 用户注意「Target name」必须手填，而且要用器件的基础名，不要带封装或温度后缀——例如 STM32F103C8。名字为空、末尾有空格、或者带了后缀，J-Link 都会拒绝连接。
  5. 解析地址
    点 Update variable addresses。变量列表里的类型和地址应当从 NOT FOUND! 变成有效值。这一列还有 NOT FOUND! 就说明符号文件不对，或者这个变量被编译器优化掉了。
  6. 把变量拖进绘图区
    从左侧列表拖到右边的绘图区。一个绘图区可以叠多条曲线；需要 X-Y 图就在新建绘图区时把类型选成 XY，再指定横轴变量。
  7. 开始采集
    确认探针接好、目标已供电，点那个写着 STOPPED 的按钮。它会变成 RUNNING，曲线开始动。
    右上角会显示探针名称、连接状态和一串 sampling: X Hz——那才是实际达到的采样率。
J-Link 首次连接较慢 从点击开始到第一条曲线出现可能要几十秒，这属于正常现象。如果一直没动静，先看日志窗口里的错误信息。

三条数据通路

理解这个软件的关键，是分清数据从哪儿来。三条通路的原理不同，适用场景也不同。

通路数据怎么来实测速率特点适合看什么
变量视图 主机逐个变量向探针索取 约 4.2 kHz（单变量） 实时；每加一个变量，所有变量一起变慢 普通控制逻辑、状态机、慢速物理量
跟踪视图 芯片通过 SWO 主动送出 由 SWO 带宽决定，可达 MHz 级 需要在代码里写 ITM 语句；对程序运行影响很小 函数耗时、中断频率、高频信号
记录器 目标的定时中断自己写进目标内存的环形缓冲 由目标侧时基决定（示例固件为 20 kHz） 录制期间不占用调试链路；支持触发与预触发；事后整块取回 比调试链路更快、且需要与事件对齐的信号

该用哪一条

  • 信号变化在几百赫兹以内，想边调边看 → 变量视图，最省事
  • 要看某段代码执行了多久、中断是不是按预期频率进 → 跟踪视图
  • 信号快到变量视图抓不住，或者想在某个条件出现时抓一段 → 记录器
变量视图的速率是怎么被限制的 软件会把普通 RAM 中重叠或严格相邻的变量合并成连续块读取，所以一段连续地址通常每个样本只需要一次探针往返。稀疏地址、外设寄存器和不支持块读取的通路会保守地退回精确读取。实际速率仍取决于探针延迟、地址布局、绘图和 CSV；同一个变量被多张图引用不会重复采集。

组与绘图区

组是最高一层容器，分两种类型：

  • Sampling group（采样组）——变量视图使用，由探针读取
  • Recorder group（记录器组）——记录器使用，由目标自己采样

只有活动组里的变量会被采集。切换活动组就等于切换看哪一批数据。

别把记录器组设为活动组 当前实现里，把记录器组切换成活动组会让采集循环去读它的变量，出现意料之外的行为。

性能诊断与 CSV 状态

采集稳定至少 1 秒且完成 100 个样本后，右上角会在确有压力时显示诊断。悬停指示器可查看请求/实际采样率、期限丢失、探针耗时、绘图缓冲等待和 CSV 队列占比。

提示含义与处理
Probe latency探针读内存占主要时间；检查连接、SWD 速度和探针型号
Address fragmentation变量地址过于分散，无法合并成少量块读取；优先把需要同时观察的数据放在连续 RAM 区域
Render contention绘图帧或缓冲复制影响采集；缩短可见时间窗、减少可见曲线或降低 GUI 负载
CSV backlog写盘跟不上或文件写入失败；检查日志目录、磁盘空间和介质速度
Deadline limited请求频率超过当前组合能稳定达到的频率，但没有单一消费者占主导；降低目标频率
CSV 过载不会停止变量采集 队列满、文件打不开或写入失败时，本轮 CSV 会停止并排空已经接受的样本，变量采集继续。右上角出现 CSV stopped，采集设置页会显示原因、时间、文件路径和样本计数。不会静默覆盖旧行，也不会自动降低采样率。

任务视图

变量视图回答"这个变量现在是多少"。任务视图回答另一类问题：谁在跑、谁在等、在等什么、等了多久。 它不读固件里的任何统计，全部从 FreeRTOS 的内核结构里读出来，所以不需要改编译选项，也不需要固件配合。

在全局设置里打开任务视图（配置文件 global.json 的 rtos.enabled）， 然后切到 Task 页签。它和变量视图共用同一次采集：探针连着、采着，任务视图才有数据。

它读的是内核自己的工作数据 就绪、延时、挂起、终止四张表，每个任务的等待对象，同步对象的持有者与等待人数， 以及运行时间统计。这些是内核自己为调度而维护的，软件只是把它们读出来并做算术。

任务表

列含义
Task任务名
Priority当前优先级。显示成 3 (1) 表示当前 3、创建时 1——这叫优先级继承：它持着一把别人想要的锁，内核临时把优先级借给它。这一列着色时也是这个意思
StateRunning / Ready / Blocked / Suspended / Terminated
Waiting on阻塞时等的对象名；读的是内核的对象等待表，不是任务表
Stack已用 / 声明大小，以及剩余百分比。数字后面带 ! 表示低于告警阈值（默认 20%，rtos.stackAlertFreePercent，设为 0 关闭）
CPU最近窗口内的处理器占用。目标没开 configGENERATE_RUN_TIME_STATS 时这一列显示"未启用"，这是目标的选择，不是软件的故障

表里一行都读不到数据时显示 -，那是"没有读数"，不是"零"。 栈水位靠宿主扫栈里的 0xa5 填充，一轮扫不完所有任务，所以每行的读数各带年龄。

同步对象与时间线

同步对象表列出内核里注册过的队列、信号量、互斥量：类型、容量、当前计数、各有几个任务在等、谁持着。 点了任务行，相关的对象会跟着高亮。

时间线把每个任务画成一条泳道，横轴与变量视图共用。跟随光标打开时，窗口跟着变量视图的光标走： 双光标是区间，单光标是居中。缺某一轮读数的任务画成"没有读数"，不画成"没在跑"——这两件事不一样。

四条诊断

面板顶部会出现几条诊断，没有问题的时候整段不出现。每条都带一小段链子，点链子里的任务名会选中表里对应的行。

诊断它说明什么什么情况下不报
优先级继承 某个持锁任务的优先级被抬高了——内核只在有更高优先级的任务等这把锁时这样做。链子读作：等待者 → 锁 → 持有者 ——
疑似死锁 两个或更多任务各自等着下一个任务手里的锁，绕成一个环 环在两轮之间自行解开时看不见——一轮只是一个采样，所以说"疑似"
就绪但从未被切入 一个任务比实际在跑的那个优先级更高，且最近两秒每一轮都是 Ready。抢占式调度器不该这样 有同级或更高优先级的任务也 Ready（调度器跑的是对的）；在跑的任务正处优先级继承中（它持着别人要的锁）；只持续了一两轮（可能是切换在途）
无超时等待 任务阻塞、但等待没有超时——它只有在那个对象被给出时才会再跑。会附带"已经等了多久" 故意挂起（Suspended）的任务；有超时的阻塞（内核知道何时唤醒它）
"不报"和"报了"一样重要 这些判据的价值首先在于不乱报。比如"Ready 却没在跑"本身是正常调度——低优先级任务本来就在等， 所以只有当一个任务的优先级高于实际在跑的那个时才算异常。判断时用的是它创建时的优先级， 因为被继承的那个号码是等待者的，不是它自己的。

切换记录：时间线是怎么来的

时间线有两种画法，取决于数据来源：

来源时间线画成代价
目标的内存环形缓冲（默认） 一条条运行区间：某个任务从被切入到被切出跑了多久 两轮之间被覆盖的记录会丢，丢了多少如实显示（lost）。条带的疏密就是这个数在说话
每轮一次的采样（没有环形缓冲时） 一个个点：那一刻谁在跑 看不到区间之间的形状

目标侧要提供切换记录，需要一处固件改动（一个 trace 宏）。参考实现与说明在 example/rtos_trace_port/event_ring/，编译开关是 make EVENTS_ON=1—— 默认不进固件，符合"不给固件加约束"这条原则。

除了内存环形缓冲，还可以走 ITM/SWO 与 RTT 两条通路 （global.json 的 rtos.eventsTransport）。它们的现状见"限制与已知问题"。

自动化接口

这个分支在上游基础上增加了两套程序接口，方便脚本与外部系统驱动它。功能开关都在全局配置文件的 api 段里，位置是 %APPDATA%/Variable-Trace/global.json。

HTTP 接口（MCP）

  • 默认地址 http://127.0.0.1:7807/mcp，只监听本机
  • 裸 JSON-RPC，不需要令牌，也不需要先握手
  • 提供 49 个工具，覆盖变量、绘图区、组、数据读取、采集、记录器、烧录、工程八大类
  • 脚本调用时注意绕开系统代理，否则会拿到代理返回的错误

命令通道

  • 裸 TCP 行协议，默认端口 7808，默认关闭
  • 面向 PLC 与控制台脚本——那些不方便讲 HTTP 的环境
  • 每行发一次请求，每行回一次应答，格式是单行 JSON
  • 与 HTTP 接口共用同一批工具和同一套参数校验
多实例并存 同时开多个程序实例时，端口会自动向后寻找空闲值。

限制与已知问题

能力边界

限制说明
只支持 32 位变量uint64_t、double 暂不支持
变量必须是全局或静态地址要在程序运行期间固定不变
采样率有上限上限取决于探针、地址布局和消费者负载；连续 RAM 变量可合并读取，稀疏或外设地址仍可能随事务数明显下降
SWD 速度并非越快越好从 1 MHz 提到 4 MHz 提升明显，4 MHz 往上收益递减
记录器需要目标侧代码固件里必须集成配套的参考实现
任务视图只能看到被调度过的东西内核不维护"切换次数"，所以没有这一列；统计的是当前状态与最近的历史
SWO 与任务视图的读数不能共存（J-Link）一颗 J-Link 同时只服务一条连接。调试连接占着它时，SWO 那条连接连不上；跟踪视图能用 SWO，正是因为它独占连接。要改用 rtos.eventsTransport 时必须接受"任务视图读不到内核"
RTT 通路当前不可用目标侧已就绪，但 J-Link 的 DLL 能找到控制块、读不出数据。默认的数据通路是内存环形缓冲，不受影响

已知缺陷

现象规避方式
把记录器组设为活动组会导致采集异常不要这样操作
J-Link 的低端型号记录器带宽被限制在 1 kHz使用变量视图；或换用支持高速采样的型号
写值计划器只能编辑，不能执行用表格图的写值列，或走 API
采集刚启动的极短时间里，记录器触发可能不响应等采集稳定后再触发

常见问题

变量地址一直是 NOT FOUND!

  • 符号文件是不是当前编译产物？拷错或者版本旧了都读不到新变量
  • 固件是不是以 debug 模式编译的？优化器可能把变量整个消掉
  • 变量有没有加 volatile？没有修饰的变量可能被优化进寄存器，内存里根本没有它的位置
  • 变量是不是定义在文件作用域？局部变量不在符号表里

J-Link 连不上

  • Target name 是否填的是器件基础名，例如 STM32F103C8；带后缀或末尾有空格都会失败
  • 目标板是否已供电
  • 上一次调试遗留的坏会话可能还占着探针。用 J-Link 自带的命令行工具执行一次连接再断开，通常能清掉

采样率比设定的低很多

界面右上角显示的是实测值，不是设定值。先悬停右上角指示器查看自动诊断：探针延迟时检查连接和 SWD 速度；地址碎片时减少稀疏地址；绘图争用时减少可见数据；CSV 积压时检查磁盘；期限受限时降低目标频率。连续 RAM 变量通常可合并读取，因此变量数不再必然造成线性下降。

跟踪视图没有数据

  • System Core Clock 有没有填对
  • 预分频是否降到了探针支持的范围以内
  • 目标固件里有没有发送 ITM 数据
  • SWO 引脚有没有接上（变量调试用的三根线不够）

记录器读回来的值不对

  • 先确认 Detect 报出的时基与固件里配的一致
  • 采样期间改过组里的变量，会导致目标侧的打包方式与主机预期不符。重新开始一次录制
  • 出现 Overrun 提示说明缓冲被覆盖过，减小变量数或者缩短录制时间

关闭时提示保存工程，程序卡住不动

有未保存的改动时会弹出确认框。用脚本自动化时要注意这一点，无人应答会一直等下去。

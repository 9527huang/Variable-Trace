# 探针租约与两种运行模式

- 文档状态：Phase 0 冻结项
- 编制日期：2026-10-22
- 上游文档：[mdkdebug Trace 接入任务视图：开发计划](mdkdebug-Trace-任务视图-开发计划.md)（§3.2、§3.3）

一颗探针同一时刻只能有一个所有者。这条规则不靠"两个程序都小心"来维持，靠一个可检测的租约文件加"打开失败就中止"。

## 一、两种模式

| 模式 | 探针所有者 | 事件去向 | 允许的事 |
|---|---|---|---|
| 交互（`viewer`） | Variable-Trace | 直接进统一模型与 UI | 采样、读事件、写录制、看变量 |
| 无人值守（`mdk`） | mdkdebug | 采集包 | 部署、编译、烧录、复位、长时间采集 |
| 交接中（`handoff`） | 谁都不完整拥有 | — | 停止采集、刷新文件、释放会话 |

无人值守模式下如果 Variable-Trace 需要实时查看，**只允许读 mdkdebug 已提交的文件块**：不得打开探针，不得推进任何游标，不得写采集包。

## 二、租约

位置：`<工程>/.variable-trace/probe-lease.json`。纯文件，不用文件锁做互斥——锁在进程被杀后不可靠，而"打开探针失败就中止"是可验证的。

```json
{
  "schema": 1,
  "leaseId": "6f1c…",
  "probeSerial": "…",
  "ownerPid": 12345,
  "ownerTool": "variable-trace",
  "mode": "viewer",
  "acquiredAt": "2026-10-22T21:03:11Z",
  "heartbeatAt": "2026-10-22T21:03:41Z",
  "epoch": 7
}
```

| 字段 | 用途 |
|---|---|
| `probeSerial` | 冲突判定的主体；不填序列号时不允许获取租约 |
| `ownerPid` + `ownerTool` | 出问题时能指出是谁 |
| `mode` | `viewer` / `mdk` / `handoff` |
| `heartbeatAt` | 存活判据 |
| `epoch` | 每次重新获得租约时递增；崩溃回收也算一次新 epoch |

心跳间隔 10 秒，超过 **45 秒**未更新视为过期。过期只说明"可以判定对方死了"，不等于"探针已经空了"——获取方仍然要真的打开探针，打不开就中止。

## 三、获取与释放

获取流程（任何一步失败都中止，不重试绕过）：

1. 读租约文件。不存在 → 新建。
2. 存在且 `heartbeatAt` 未过期，且 `ownerPid` 是存活进程 → **拒绝**，UI 说明谁在用、什么模式、多久没心跳。
3. 存在但过期，或 `ownerPid` 已不存在 → 回收：`epoch = 旧 epoch + 1`，写新租约，记一条审计日志。
4. 打开探针会话（SWD/RTT/SWO 任一）。失败 → 立即释放刚写的租约，报错。
5. 采集开始后，每 10 秒更新 `heartbeatAt`。

释放流程：停止采集 → 刷新文件 → 关闭会话 → 把 `mode` 置 `handoff` 并写入 `releasedAt` → 删除租约文件。删除失败不算成功释放，要报错。

## 四、交接状态机

```
Idle
 ├─ viewer: 取租约(mode=viewer) → 采集中 → 释放 → Idle
 └─ mdk:    取租约(mode=mdk)    → 部署/烧录/采集 → 释放 → Idle

viewer → mdk（或反向）
  持有方停止采集并落盘
  → mode = handoff，写 releasedAt
  → 关闭探针会话
  → 删除租约
  → 另一侧按 §3 重新获取（epoch+1）
```

交接期间两侧都不能采集。`handoff` 状态存在时间上限（30 秒），超过则由下一个获取者强制回收并记一条 `handoff-timeout`。

## 五、崩溃与异常

| 情况 | 处理 |
|---|---|
| 持有方进程被杀 | 45 秒后租约过期；回收时 `epoch+1`；探针可能仍被旧进程的驱动占用 → 打开失败即中止，提示"探针仍被占用，请复位或重插" |
| 探针被拔 | 采集报错退出，释放租约；**不**把这次采集标成成功 |
| 探针被换（序列号变了） | 旧租约作废，新租约从 `epoch 1` 开始；UI 明确提示换了探针 |
| 系统时间被调 | 心跳用单调时钟比较，落盘时间只作展示；两个时间都写在租约里 |
| 两个 Variable-Trace 同时启动 | 第二个在 45 秒内被拒；45 秒后回收，第一个下次心跳发现 `leaseId` 变了，立即停止采集并报错（不静默继续） |

## 六、与事件模型的关系

- 每次成功获取租约（含回收）产生新 `epoch`，**目标侧 epoch 与租约 epoch 不是同一个东西**：目标是目标复位/重烧，租约是主机侧所有权变更。两个都要记，日志里分别写 `targetEpoch` 与 `leaseEpoch`。
- 租约变更导致的采集中断，在 Findings 里报 `acquisition-interrupted-by-lease`，不算数据丢失。

## 七、冻结状态

1. 租约是文件，不做文件锁互斥。
2. 心跳 10 秒，过期 45 秒。
3. 过期只允许"尝试"，不允许"假定探针已空"。
4. 每次获取与回收都递增 `epoch` 并留审计日志。
5. 交接 30 秒上限，超时强制回收。
6. 无人值守模式下 Variable-Trace 只读已提交块。
